# 7 BOOM Configurations for PD Agent Training

## Context

ArchGen AI's PD agent needs a diverse but compact training set of RISC-V processor designs. Each config must stress a **different physical design challenge** — varying macro count, routing density, timing criticality, and floorplan topology. All configs come from the same BOOM codebase, generated by changing parameters in `src/main/scala/v4/common/config-mixins.scala`.

---

## The 7 Configurations

### 1. SmallBoom (Baseline — Easy)
**PD Challenge**: Few macros, relaxed constraints. Tests agent's ability to find a clean, efficient solution when the problem is easy.
- **Config**: `WithNSmallBooms` (stock)
- **Profile**: 1-wide, 32-entry ROB, 8-entry LDQ/STQ, 4KB D$/I$ (64 sets × 4 ways)
- **Expected macros**: ~20-30 (small regfiles, small SRAMs)
- **Why**: Establishes baseline. If the agent can't close timing here, nothing else matters.

### 2. MediumBoom (Moderate — Balanced)
**PD Challenge**: Medium macro count with moderate routing congestion. Tests balanced placement.
- **Config**: `WithNMediumBooms` (stock)
- **Profile**: 2-wide, 64-entry ROB, 16-entry LDQ/STQ, 80 int / 64 FP physical regs, banked int regfile (2 banks)
- **Expected macros**: ~50-70
- **Why**: Representative "typical" design — enough complexity to be interesting, not overwhelming.

### 3. LargeBoom (Hard — Dense Routing)
**PD Challenge**: Column ALU issue creates dense feedback paths between ALU execution units and issue queues. Tests routing congestion management.
- **Config**: `WithNLargeBooms` (stock)
- **Profile**: 3-wide, 96-entry ROB, 24-entry LDQ/STQ, 100 int / 96 FP phys regs, 8-way D$/I$ (128-bit rows), `enableColumnALUIssue=true`
- **Expected macros**: ~80-120
- **Why**: Column ALU routing creates locality constraints — ALU results must feed back to specific issue columns. Agent must co-locate ALU logic without creating routing hotspots.

### 4. MegaBoom (Very Hard — Many Large Macros)
**PD Challenge**: Maximum macro count and size. 4-bank D-cache, 2-wide LSU, large regfiles (144 int, 128 FP, 4 banks). Tests floorplanning with many large SRAM blocks.
- **Config**: `WithNMegaBooms` (stock)
- **Profile**: 4-wide, 128-entry ROB, 32-entry LDQ/STQ, 4-bank D-cache, 40-entry ALU IQ, 32-entry FP/MEM IQs
- **Expected macros**: ~130-180
- **Why**: This is your Ariane-class complexity. Large SRAMs fight for die space. Agent must handle macro-dominated floorplans where placement determines routability.

### 5. MegaTapeoutBoom (Very Hard — Constrained Ports)
**PD Challenge**: Same scale as MegaBoom but with `singlePorted=true` for I$ and D$ SRAMs, plus different predictor (FastTAGE with 6 TAGE tables + SlowBTB + 2048-entry BIM). Tests how agent handles single-ported SRAM timing constraints and a complex frontend macro cluster.
- **Config**: `WithNMegaTapeoutBooms` (stock)
- **Profile**: 4-wide, single-ported caches, 4-bank FP freelist, agen stage, ALU single-wide dispatch, 128-set D$ (vs 64 in Mega — bigger SRAM)
- **Expected macros**: ~140-200 (more predictor tables = more SRAMs)
- **Why**: Single-ported SRAMs mean tighter timing constraints on cache access paths. The 6-table TAGE + SlowBTB + 2048-set BIM creates a dense SRAM cluster in the frontend. Agent must separate frontend and backend macro clusters while maintaining timing.

### 6. GigaBoom (Extreme — Widest Core)
**PD Challenge**: 5-wide decode/dispatch/commit with 5-wide ALU issue. Extreme interconnect fanout. Tests agent's handling of wide datapaths and many parallel execution units.
- **Config**: `WithNGigaBooms` (stock)
- **Profile**: 5-wide, 130-entry ROB, 32-entry LDQ/STQ, column ALU (5 columns), 128 int/FP phys regs
- **Expected macros**: ~120-160
- **Why**: The 5-wide issue width creates massive crossbar/mux structures. Routing congestion is the dominant challenge, not macro count. This is the opposite of config #4 — fewer macros but harder routing.

### 7. MediumBoom + No FP (Asymmetric — Area Constrained)
**PD Challenge**: Removing the FP unit eliminates ~30% of the design's area (FP regfile, FMA units, FP issue queue), creating an asymmetric layout with a "hole" where FP logic would be. Tests agent's ability to exploit freed area efficiently.
- **Config**: Custom — MediumBoom with `fpu = None, usingFPU = false`
- **Profile**: 2-wide, 64-entry ROB, no FP pipeline, no FP regfile
- **Expected macros**: ~30-40 (significantly fewer than stock Medium)
- **Why**: Most PD agents train on designs where all functional units exist. This asymmetric design tests generalization — can the agent handle a fundamentally different macro topology?

## Summary: What Each Config Stresses

| # | Config | Macros | Primary PD Challenge |
|---|--------|--------|---------------------|
| 1 | SmallBoom | ~25 | Baseline / easy timing closure |
| 2 | MediumBoom | ~60 | Balanced placement + routing |
| 3 | LargeBoom | ~100 | Dense ALU feedback routing (column issue) |
| 4 | MegaBoom | ~150 | Many large SRAMs, macro-dominated floorplan |
| 5 | MegaTapeout | ~170 | Single-ported SRAM timing + complex BPD cluster |
| 6 | GigaBoom | ~140 | Wide crossbar routing congestion |
| 7 | Medium-NoFP | ~35 | Asymmetric topology, area optimization |

## How to Generate

Configs 1-6 are stock — use them directly in Chipyard:
```scala
class MySmallBoomConfig extends Config(
  new boom.v4.common.WithNSmallBooms(1) ++
  new chipyard.config.AbstractConfig)
```

Config 7 (no FP) requires a custom override:
```scala
class NoFPMediumBoomConfig extends Config(
  new Config((site, here, up) => {
    case TilesLocated(InSubsystem) => up(TilesLocated(InSubsystem), site) map {
      case tp: BoomTileAttachParams => tp.copy(tileParams = tp.tileParams.copy(
        core = tp.tileParams.core.copy(fpu = None, usingFPU = false)))
      case other => other
    }
  }) ++
  new boom.v4.common.WithNMediumBooms(1) ++
  new chipyard.config.AbstractConfig)
```

## Verification (3 Levels)

### Level 1: RTL Correctness (once per config)
Confirms the processor is functionally correct before any PD work.

| Method | What It Tests | How to Run |
|--------|--------------|-----------|
| riscv-tests (ISA) | Every RV64GC instruction | `make run-asm-tests-fast` in Chipyard |
| CSmith (random C) | Random programs compared vs Spike reference | `util/csmith/run-csmith.sh` (50 iterations) |
| Benchmarks | CoreMark, dhrystone | `make run-bmark-tests-fast` in Chipyard |
| TraceGen | Memory ordering (loads, stores, LR/SC, AMOs) | `lsu/tracegen.scala` — special trace injection tile |
| Embedded asserts | Microarchitectural invariants in ROB, LSU, issue units | Fire automatically during any simulation |

**Config 7 (No-FP) note**: Run only `rv64ui` + `rv64um` ISA subsets (skip `rv64uf`/`rv64ud`).

### Level 2: Synthesis Verification (once per config)
Confirms the design synthesizes to a valid gate-level netlist.

- Synthesize via Yosys (open-source) or Design Compiler (commercial)
- Check: no unmapped cells, no inferred latches, no synthesis errors
- Check: SRAM macro count matches expectations (~25 to ~200 per config table above)
- Check: gate count and area estimates are reasonable
- Output: netlist + macro list → feeds into PD agent

### Level 3: PD Verification (every PD agent iteration)
Validates physical design quality — this is what the PD agent's analyzer does each run.

| Metric | Tool/Command | Pass Criteria |
|--------|-------------|---------------|
| Setup timing (WNS) | `report_checks` | WNS >= 0 ns |
| Hold timing | `report_checks -path_delay min` | No hold violations |
| Total Negative Slack (TNS) | `report_checks` | TNS >= 0 ns |
| DRC violations | `detailed_route` report | 0 violations |
| Routing congestion | Congestion heatmap | No unroutable regions |
| Power | `report_power` | Within target envelope |
| Area / utilization | `report_design_area` | Matches die target |

### Verification chain for training data

```
RTL correct? ──→ Synthesis clean? ──→ PD agent runs ──→ PD metrics valid?
  (once/config)    (once/config)      (many iterations)   (each iteration)
```

Levels 1-2 produce a fixed, verified netlist per config. Level 3 is where RL training happens — your agent iterates on placement/routing and the analyzer validates each attempt.
